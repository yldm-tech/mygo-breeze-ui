# Breeze UI for MyGo

`github.com/yldm-tech/mygo-breeze-ui/ui/breeze` draws [MyGo](https://github.com/egoist/mygo)'s native UI widgets as the desktop the app runs on draws its own controls: macOS's on a Mac, Windows 11's on Windows and GNOME's libadwaita controls on Linux.

Its widgets have the names and signatures of package `ui`'s. A view swaps `ui.Button` for `breeze.Button` and keeps everything else: the widgets return `ui.Element`, answer `Clicked`, and take more styles after the call as `ui`'s do.

```go
import (
	"github.com/egoist/mygo/ui"
	breeze "github.com/yldm-tech/mygo-breeze-ui/ui/breeze"
)

func (app *settings) view(c *ui.Context) {
	breeze.Use(c) // the platform's colors and metrics, for package ui's widgets too
	ui.Column(c).Padding(16).Gap(12).Children(func() {
		breeze.Checkbox(c, &app.remember, "Remember me")
		breeze.Switch(c, &app.sync).Label("Sync")
		ui.Row(c).Gap(8).Children(func() {
			breeze.Button(c, "Cancel")
			if breeze.PrimaryButton(c, "Save").Clicked() {
				app.save()
			}
		})
	})
}
```

## Install

```sh
go get github.com/yldm-tech/mygo-breeze-ui
```

It needs MyGo v0.7.4 or later. The gallery shows the three platforms side by side:

```sh
go run ./examples/breeze-ui
```

## Storybook

[The storybook](https://yldm-tech.github.io/mygo-breeze-ui/storybook/) shows every widget as Storybook shows components: stories in a sidebar, each drawn as macOS, Windows 11 or GNOME draws it, or as the three side by side, light or dark, with controls for its arguments and the Go that builds it. bun run site:build

```sh
cp "$(go env GOROOT)/lib/wasm/wasm_exec.js" website/dist/storybook/
```

## Widgets

Each group of widgets, those of one `widgets_<group>.go` file or of `widgets.go` and `extras.go`, has a page in [`docs/widgets`](widgets) that tells how they look on each platform, where those looks come from and the group's own limits. The [website's catalog](https://yldm-tech.github.io/mygo-breeze-ui/#catalog) lists every widget, and [the storybook](https://yldm-tech.github.io/mygo-breeze-ui/storybook/) shows them.

The pointer, the keyboard, the focus and accessibility are MyGo's. The buttons, choices, slider, segments and tabs are built on MyGo's bases without a look (`ui.ButtonBase`, `ui.ToggleBase`, `ui.CheckboxBase`, `ui.RadioBase`, `ui.SwitchBase`, `ui.SelectBase`, `ui.SliderBase`, `ui.SegmentedBase`, `ui.TabsBase`), so screen readers, Tab, Space and the arrows work as they do for `ui`'s widgets. The text fields are `ui`'s own, with the box around their text drawn by the platform, so editing, input methods, the search field's clear button and Escape are MyGo's. `TextInputBuffer` and `TextAreaBuffer`, which edit a `ui.TextBuffer` without copying the whole document, are `ui`'s buffer inputs in the box `TextInput` and `TextArea` draw, the same code drawing both: MyGo styles a buffer input as it styles `ui.TextInput`, so the two draw the same pixels on every platform, and the buffer's editing, undo, selection and composition stay MyGo's. `Disabled(true)` grays a widget out: MyGo draws disabled elements at half opacity, which is how libadwaita draws them, but libadwaita fades a control as a whole (`filter: opacity`) where MyGo fades each part it paints, so where parts overlap the part below shows through: a disabled checked box's check mark is light blue rather than white, and a disabled switch's slider is #f5f5f6 where libadwaita's is #fdfdfd (measured with `tools/adwaita-reference`). AppKit and WinUI have disabled colors of their own instead (AppKit's `tertiaryLabelColor` labels, gray default buttons and accent controls at about 70%; WinUI's `*Disabled` brushes such as `TextFillColorDisabled`), which Breeze UI cannot draw while MyGo halves every disabled element's opacity; half opacity comes close to them. A disabled checked box or chosen radio button on macOS is gray, as AppKit draws it, and so is a disabled checked box on Windows, as WinUI draws it, though its check mark can only come to 223 where WinUI's is white.

`Table`, `OutlineTable`, `Outline`, `Tree`, `TreeItem` and `GridView` keep MyGo's rows, cells, scrolling, keys and selection; Breeze UI draws the platform's rows over MyGo's frames from elements inside them, as MyGo does not clip what an element draws to its box. `NumberInput` is rebuilt on breeze's text field and two `ui.ButtonBase`s with MyGo's parsing, clamping and keys; `CheckboxGroup` on `ui.CheckboxBase` with the platform's mixed mark. `RadioGroup` is `ui.RadioGroup`'s own group, its focus, arrows, role and name MyGo's, with the platform's spacing between its radio buttons. `MenuButton`'s and `PopoverMenuButton`'s buttons are the platform's; the menu of `MenuButton` is the system's own, and `PopoverMenuButton`'s is MyGo's in the platform's menu colors and corners, until MyGo releases a `MenuBase`. `Stepper` keeps MyGo's arrows and behavior inside the platform's box. `PasswordField` is `ui.TextInput` with `Password`, which MyGo calls each frame the text is hidden: its editing, Enter and what assistive technology hears are MyGo's, and Copy and Cut take nothing while the text is hidden. Windows's RevealButton is a box named "Show Password" and checked while the text shows, which keeps the focus in the field as WinUI's is not a Tab stop; Alt+F8 reveals the text from the keyboard. GNOME's Show Text is a check item after MyGo's editing items of the field's context menu. `SplitButton` is two `ui.ButtonBase`s in a group, the second with `Element.Menu`, so its menu is the system's own, as `MenuButton`'s; `IconButton` is `Button` with an empty label, its icon as the child and its label as the name, with the platform's tooltip. `breeze-ui list` shows which widgets are drawn and which are themed.

Some drawn widgets keep MyGo's parts that no base reaches: the headers of `Accordion`, the popup of `Combobox`, and the chips of `TokenField`. [What MyGo would need](#what-mygo-would-need) lists the bases that would let Breeze UI draw them.

## Platforms

`breeze.Current()` is the platform the app runs on: `Mac` on macOS, `Windows` on Windows and `Linux` elsewhere. Every widget looks it up when it is built.

- `breeze.SetPlatform(breeze.Windows)` makes every window draw another platform's controls, as for screenshots; `breeze.SetPlatform(breeze.Auto)` follows the system again.
- `breeze.Preview(c, p, body)` draws only what `body` builds as platform `p`, in this window. With `ui.Themed(c, breeze.Theme(c, p))` around it, a gallery shows the platforms side by side:

```go
for _, p := range breeze.Platforms {
	breeze.Preview(c, p, func() {
		ui.Themed(c, breeze.Theme(c, p)).Grow(1).Padding(16).Gap(12).Children(func() {
			breeze.Button(c, "Cancel")
			breeze.Switch(c, &app.sync).Label("Sync")
		})
	})
}
```

## Themes

`breeze.Theme(c, p)` returns platform `p`'s theme for the window's appearance: the window background, text, separators and accent of macOS, Windows 11 or GNOME, light or dark. `breeze.Use(c)` sets it for the window with `c.SetTheme`, so package `ui`'s widgets and elements of your own that read `c.Theme()` follow it too.

Like MyGo's default theme it follows the desktop's preferences:

- **Accent color.** The accent the user chose replaces the platform's default (`#007aff`, `#0078d4`, `#3584e4`). On Windows the controls are filled with the shade WinUI uses, darker in the light theme and lighter in the dark one.
- **Higher contrast.** Separators and secondary text are darker in the light theme and lighter in the dark one, and the focus ring is opaque.
- **Text size.** The font size grows with Windows's and GNOME's text scale.

`breeze.ThemeOf(c, p, dark, accent)` returns the same theme in the appearance `dark` names, whatever the window's is, with `accent` in place of the user's accent (`ui.Color{}` keeps the user's). `breeze.Theme(c, p)` is `breeze.ThemeOf(c, p, c.Theme().Dark, ui.Color{})`. The platform derives the rest from the accent as it does from the system's: the accent controls' fills under the pointer and pressed, the focus ring where the platform tints it, and on Windows the shades WinUI fills its controls, links, InfoBar icons and toasts with. With `ui.Themed` it builds a part of a window in the other appearance or in an app's own accent, as a dark player in a light window; higher contrast and the text size still follow the desktop:

```go
p := breeze.PlatformOf(c)
ui.Themed(c, breeze.ThemeOf(c, p, true, ui.Color{})).Grow(1).Children(func() {
	breeze.Button(c, "Play")
	breeze.Segmented(c, &app.speed, "1×", "1.5×", "2×")
})
ui.Themed(c, breeze.ThemeOf(c, p, c.Theme().Dark, ui.Hex("#8e44ad"))).Background(ui.Transparent).Children(func() {
	breeze.PrimaryButton(c, "Subscribe")
})
```

## Limits

- **Inactive windows.** AppKit draws an inactive window's accent controls (checked boxes, chosen radio buttons, on switches, an on toggle, the chosen segment and the default button) in gray. MyGo v0.7.4 does not tell a view whether its window is active, so Breeze UI always draws the key window's look: a `HeaderBar` keeps its active look too, where AppKit dims an inactive window's title, WinUI's TitleBar turns its title to `TextFillColorTertiary` and its headers half opaque (`TitleBarDeactivatedOpacity` 0.5), and an AdwHeaderBar in the backdrop takes `headerbar_backdrop_color` with its content at 50% opacity.
- **Liquid Glass surfaces.** Menus, popovers, tooltips and NSAlert's panel are separate windows of macOS 27's glass material, which AppKit does not render offscreen and which could not be captured from a live window either (a popover's window is not listed, a tooltip shows only under the pointer): they are drawn to resemble macOS 26's, not measured.
- **Sizes.** The platforms' controls differ in size: a macOS push button is 24 points high, Windows's 32 and GNOME's 34, and a GNOME scale is 34 pixels high with its padding (28 with marks after it). The same layout is denser on a Mac; size elements around the widgets from the content rather than with fixed heights.
- **Windows and GNOME fidelity.** The macOS look is compared with AppKit's rendering on macOS 27.2, pixel by pixel. The Windows look of the controls of the screenshot test is compared with WinUI 3.3's rendering on Windows 11 26H2 (`tools/winui-reference`); what it could not compare is taken from WinUI's sources: the focus visuals (nothing has the keyboard's focus in the render), the ContentDialog's smoke layer (left out when the dialog is shown in place, as it must be to be rendered at 2x), the drop-down of the ComboBox and other menus, the check mark's stroke (WinUI's animated icon renders without antialiasing there; its area suggests about 1.35 DIPs where the source gives 1.225), and the widgets of the `widgets_*.go` and `drawn_*.go` files but for `PasswordField`, `SplitButton`, `IconButton`, `InfoBar`, `ProgressRing`, `Card`, `ActionRow`, `SwitchRow`, `ComboRow`, `EntryRow`, `SpinRow`, `ExpanderRow`, `TabView`, `HeaderBar` and `Text`, which are compared with WinUI's PasswordBox, SplitButton, Button, CommandBar, InfoBar, ProgressRing, CommunityToolkit's SettingsCard and SettingsExpander (holding a ComboBox, TextBoxes and NumberBoxes), TabView, TitleBar and the TextBlock styles (and `StatusPage`'s text with the type ramp) in the same way. Of those, what still differs: the bullets of a PasswordBox (MyGo's), the icons of the tests (SVGs, not Segoe Fluent Icons), the informational InfoBar's fill by a level, the text's line height, the header of an `AccordionItem` and the disabled colors (WinUI's disabled icon button reads 245 with a 229 edge and a 157 icon, Breeze UI's at half opacity 247, 238 and 136; a disabled SettingsCard keeps its card). Text is not compared glyph by glyph: WinUI's is DirectWrite's Segoe UI Variable, Breeze UI's is the host's font through MyGo (Segoe UI on Windows), so labels sit where WinUI puts their text box and differ by the fonts' ascents elsewhere; the render lays out in whole DIPs, where WinUI at 200% rounds to half DIPs. The GNOME look is compared with libadwaita 1.10.0's rendering (GTK 4.24.1), pixel by pixel, for the controls of every screenshot test that libadwaita has: those listed under GNOME above. That includes the widgets MyGo lacks, `PasswordField`, `SplitButton`, `IconButton`, `InfoBar`, `StatusPage`, `Card`, `ActionRow`, `SwitchRow`, `ComboRow`, `EntryRow`, `SpinRow`, `ExpanderRow`, `TabView`, `HeaderBar` and `Text`, against GtkPasswordEntry, AdwSplitButton (raised and in a `.toolbar`), image buttons, AdwBanner, AdwStatusPage, `.card`, AdwActionRow, AdwSwitchRow, AdwComboRow, AdwEntryRow, AdwSpinRow and AdwExpanderRow in a boxed list, an AdwPreferencesGroup, AdwTabBar, AdwHeaderBar, and labels of the type ramp's classes; `ProgressRing`, which libadwaita does not have, is compared only for AdwSpinner's track and stroke and GtkProgressBar's accent. Not compared there: what shows only under the pointer, pressed or with a menu open (GTK's tooltips, the split button's menu, a switch row's hover), the password entry's Show Text item, and the bullets, which differ (see Password fields). GTK rounds alpha to whole levels, so the dark theme's card, white at 8%, reads 51 where Breeze UI's is 52; the entries' and buttons' translucent faces, white at 10%, read 57 in both. Where GNOME's look depends on text, Breeze UI follows the font it is given rather than Adwaita Sans, so a control after a label moves with the label's width. MyGo curves rounded corners as Apple does when it runs on macOS (`continuousCorners` in its `paint.go`) and circular elsewhere, so the GNOME and Windows looks rendered on a Mac, as most screenshots compared here were (the GNOME settings rows, tab bar and header bar were compared rendered on Linux too), show corners that reach a few device pixels further along their edges than GTK's and WinUI's (along the edge of a tab with corners of 9, the fill reaches its full color 14 device pixels into the corner at 2x, GTK's 5), while on Linux and Windows they are drawn as those toolkits draw them. libadwaita 1.10.0 draws a GtkLevelBar's `.low` block in the accent color, a later rule of `_level-bar.scss` overriding the warning color; `Meter` keeps the warning and error colors for its levels, as GtkLevelBar has no level that is bad when high. Some values are inferred rather than read: the padding of an accent button and the line height of 14-pixel text on Windows, the ProgressRing's starting angle, the ComboBox's item height, the BreadcrumbBar's chevron (a Segoe Fluent Icons glyph), and the spacing of toggles in a `ToggleGroup`, as WinUI has no joined toggles. Windows's default accent takes the shades Windows gives it; for a custom accent the shades (link colors and fills) are mixes that come within a few levels of the default accent's.
- **What only MyGo draws.** The arrows of `Stepper`, the search field's magnifying glass (at the start of the field, where WinUI's AutoSuggestBox puts its query button at the end), the caret (in the accent on every platform, where macOS 27 draws a 2-point accent caret and GNOME the text color) and the rows of `PopoverMenuButton`'s menu (their height and padding; their corners follow the theme's radius, 13 on GNOME against libadwaita's 9) are MyGo's, and on GNOME that menu has no arrow pointing at its button, where GtkMenuButton's popover has one.
- **Scroll bars.** MyGo shows a container's thumb while the pointer is over the container or drags it, 3 DIPs in from the edge, at least 24 long, 2 DIPs wider while dragged, with no track or arrows. The platforms differ: macOS's overlay scroller (17 points wide, measured with `NSScroller.scrollerWidth` on macOS 27.2) paints a 7-point knob with a faint 1-point outline 1 point in from its edge, shows it while the view scrolls and widens it under the pointer; WinUI's ScrollBar is a 2-pixel indicator that grows after 0.4 seconds under the pointer into a 12-pixel bar with a track and small arrow buttons and contracts 2 seconds after it leaves; GNOME's overlay scroll bar is a 3-pixel slider 4 pixels in from the edge that grows into an 8-pixel slider over a 10% trough under the pointer, at least 40 long, with a 1-pixel outline.
- **Icons and fonts.** Breeze UI ships no SF Symbols, Segoe Fluent Icons or Adwaita icons: check marks, chevrons and arrows are drawn as paths, and the search field's magnifying glass is MyGo's. Text uses the system's font (`Font: ""`).
- **Parts MyGo draws inside a widget.** Without a base for them, these stay MyGo's in the platform's theme: the accordion's headers (SwiftUI puts the chevron before a regular-weight title, an Expander's header is 48 high, an AdwExpanderRow 55 high with its separator, a regular-weight title and an accent arrow when open, its rows on `card_shade_color` at 50%), the popup of `Combobox` (highlighted in the accent, not the platform's menu), the chips of `TokenField` (gray, not NSTokenField's flat blue tokens), the headers of `Table` and `OutlineTable`, the arrow of `TreeItem`, MyGo's fixed row geometry (a `Table` row is at least 32 high where AppKit's is 24, and `Outline`'s content starts about 13 points right of AppKit's), the room after the date of `DateInput` on macOS (14 DIPs where MyGo's icon was), the colon of `TimeInput` (muted, where AppKit draws it in `labelColor`) and the dividers of WinUI's TimePicker. The Windows label of `Field` and the GNOME legend of `Fieldset` are drawn over MyGo's at their platforms' weights: the Windows label does not dim when only its control is disabled.
- **Themes of a part of a window.** A subtree built with `ThemeOf` draws its controls in its own appearance and accent, but not what the window draws itself: the traffic lights of macOS and GTK's title buttons keep the window's appearance, as MyGo's `SetWindowButtonsTheme` reaches only Windows's caption buttons. A macOS link keeps AppKit's `linkColor`, which does not follow the accent. On Windows the links, InfoBar icons and toasts inside take the theme's accent when it is one `ThemeOf` or `Theme` made, or a copy of one, told by its selection color and its accent fill; a Windows theme whose `Accent` an app replaced afterwards keeps the user's accent for them, so give the accent to `ThemeOf` rather than setting it on the theme.
- **Pressed rows.** `List`, `Table`, `Outline` and `GridView` draw chosen and hovered rows as each platform does but not pressed ones, as MyGo's rows do not report a press.

## What MyGo would need

MyGo v0.7.4 is the latest release. These additions to it, in the style of its existing bases (`CollapsibleBase`, `TabsBase`, `ToastBase`), would let Breeze UI draw what it cannot yet:

- **Disabled colors.** A per-theme or per-element switch for the half opacity of disabled elements (`paint.go`, with `Element.Opacity` clamped to 1), so that AppKit's and WinUI's disabled colors can be drawn while GNOME keeps the halving.
- **Theme tokens.** The focus ring's width, offset and an inner stroke (AppKit's ring is 3.5 points flush outside the shape, libadwaita's 2 pixels inside it, WinUI's two strokes); the caret's color and width; the selected text's color; the scroll bar's inset, width under the pointer, track, outline and minimum length; the label weight of `Field` and the legend weight of `Fieldset`; a badge's text size; `Themed` without resetting the inherited text style.
- **Scroll bars.** A way for an element to draw its scroll container's bars, as `Scrollbars(false)` hides them, while MyGo keeps their behavior (MyGo's public `ui.Scrollbar` and `Painter.Scrollbar`, for views that scroll themselves, paint the same fixed thumb and take only `ScrollbarState{Dragging, Color}`, so they cannot draw another look either): a callback such as `Element.DrawScrollbars(func(p *Painter, bar ScrollbarPaint))` given, for each bar, its orientation, track and thumb boxes, whether the pointer is over the bar itself (not only the container), over the thumb, pressing or dragging it, and how long ago the content last scrolled, together with per-element geometry that MyGo's hit testing and thumb arithmetic follow: the bar's width at rest and under the pointer, its inset from the edge, the thumb's least length, and optional arrow buttons that step by a line and repeat while held. With it Breeze UI could draw macOS's overlay knob (7 points with its outline, appearing while scrolling and widening under the pointer), WinUI's ScrollBar (the 2-pixel indicator expanding into a 12-pixel bar with its `AcrylicInAppFillColorDefault` track, 8-pixel arrow glyphs and corners of 3, `ScrollBar_themeresources.xaml`) and GNOME's overlay scroll bar (the 3-pixel slider growing to 8 over a 10% trough, at least 40 long, `_scrolling.scss` of libadwaita 1.10.0), and draw `Scroll`, `ScrollBoth` and `ScrollHorizontal` itself.
- **Bases.** `AccordionItemBase` (the headers with MyGo's Up, Down, Home and End and its focus ring), `RangeSliderBase` (or `Element.NamedAfter`, so knobs are named after the slider, and a way to read which knob has the focus), `NumberInputBase` and `DecimalInputBase` (with MyGo's localized errors), `CalendarBase` (with `Browse`), `FindBarBase`, `ColorPickerBase`, `EditableTextBase`, `DateInputBase` and `TimeInputBase` (the icon, the segments and their places), `CheckboxGroupBase` (so `ui.Checkbox` boxes count too), and a `MenuBase` or a menu style for drawn menus and the popups of `Combobox` and `Autocomplete`.
- **Rows and cells.** `ListRow.Pressed`, a cell builder for `Table` with the cell's box and state, `ListState.RowHeight` and a header cell builder, `OutlineRows` with the row and its arrow, `GridState.Chosen` and `Element.IsSelected`, readable while painting.
- **Toolbars and fields.** A way to know a control is built in a toolbar and to style its items and overflow button, overlays that do not inherit the toolbar's look, and the field forwarding of `Combobox` (`Element.NameFrom`, `Element.FocusTo`) with an option not to highlight the first match.
- **MyGo's own strings.** An exported way to read the strings of its controls in the window's language, with an app's `mygo.*` overrides (its internal `l10n` package): with it, `DecimalInput`, `FindBar` and `ColorPicker` could be rebuilt from the bases MyGo already exports, and `Calendar` too but for `Browse`.
- **Paths.** `Path.ArcTo`, to stroke GTK's icons exactly.
- **Windows.** Whether the window is active (it is kept internally, `windowFocused` in `runtime.go`, but not exported), for the inactive looks of AppKit's controls and of the title bars; and a way for `ui.Tester` to report a window drag and a title bar double click, so that tests can check `DragWindow`.

## Adding a widget

Each group of widgets keeps its own files, so that pull requests adding widgets to different groups do not touch the same files. A new group `foo` is new files only:

- `ui/breeze/widgets_foo.go`: the widgets.
- `ui/breeze/widgets_foo_test.go`: its tests, with an `init` function adding the widgets Breeze UI draws to `drawnWidgets`, and `TestScreenshotsFoo` writing their screenshots.
- `ui/breeze/catalog/foo.json`: `{"components": [...]}`, an entry for each exported function of `widgets_foo.go`, with an example calling it (`TestCatalogMatchesWidgets` checks the two against each other).
- `docs/widgets/foo.md`: the page of the group, with its sections Looks, Sources, Limits and, if it has any, What MyGo would need, naming each widget (`TestWidgetDocs`).
- `examples/storybook/stories_foo.go`: the stories, added to `storyGroups` in an `init` function.
- `tools/appkit-reference/Sources/appkit-reference/Scenes/foo.swift`: a `SceneGroup` subclass rendering AppKit's counterparts, with the delegates only it uses.
- `tools/winui-reference/Scenes/foo.cs`: a method of `App` marked `[Scenes]` returning WinUI's, with the hooks only it uses.
- `tools/adwaita-reference/scenes/foo.py`: the group's `SETS` of libadwaita's.

Adding widgets to an existing group changes only that group's files. The code the groups share, `widgets.go`'s helpers, `mac.go`, `fluent.go`, `adwaita.go` and the `drawn_*.go` files, changes only to generalize a helper or take one out of a group's file; such a change goes first in a pull request of its own. `ui/breeze/catalog/platforms.json`, the reference tools' own files (`main.swift` and `Support.swift`, `Program.cs`, `reference.py` and `common.py`) and the sections of this page do not change for a widget. The catalog is merged from its files where it is used: `packages/breeze-mcp/catalog.json` is built, not committed.
